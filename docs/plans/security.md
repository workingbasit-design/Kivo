## B0. Current posture (verified in code, 2026-10-14)

- **Headers:** HSTS (2yr+preload), X-Frame-Options SAMEORIGIN, nosniff, Referrer-Policy, Permissions-Policy (camera/mic off, geolocation self). **CSP: absent** — documented as intentional in `next.config.ts` (Next.js inline scripts). SAMEORIGIN (not DENY) is deliberate for future booking-page embedding.
- **Auth:** custom sessions (`kivo_session` cookie, httpOnly, Secure in prod, SameSite=Lax). Generic login errors (Part A8). Passwords: business min 15 chars (via `src/lib/password-policy.ts`), customer min 8. Bcrypt 12 for business; customer uses PBKDF2-SHA512 100k. Rate limiting is DB-backed (`RateLimit` table) — the audit's in-memory gap is closed. Password reset: 1h TTL, SHA-256, single-use, invalidates sessions.
- **Missing entirely:** TOTP/2FA (zero matches), error tracking/Sentry (zero matches), CAPTCHA/Turnstile (honeypot + min-fill-time only, on the review form), breached-password check (zero matches), business email verification (zero matches), session rotation (zero matches).
- **`?next=`:** `safeNext()` already exists and is used by customer login — verify it rejects absolute/foreign URLs in implementation; do not assume.
- **`dangerouslySetInnerHTML`:** 5 sites. 4 are JSON-LD via `JSON.stringify` (safe — no user content in the JSON). 1 is `src/app/help/[slug]/page.tsx:116` rendering `renderBody(loc.body)` — help articles are admin-authored, but the renderer must be checked for sanitization (see B5).
- **Server-side fetch of user-controlled URLs:** outgoing webhooks (`src/lib/webhooks.ts` — endpoint URL is user-supplied, validation is only `https://` prefix, NO internal-address blocking → SSRF risk, see B1). Other fetches are fixed URLs (holidays API, weather, maps, places) — not user-controlled.
- **Secrets at rest:** Google + QuickBooks OAuth tokens PLAINTEXT in DB (see Part A, M7 note + B4). Messaging tokens AES-256-GCM encrypted. API keys / tokens SHA-256 hashed.
- **Tokens:** portal tokens, review tokens, signing tokens, agent keys — SHA-256 hashed, single-use/expiring (verified in schema comments). Confirm each is ≥128 bits from `crypto.randomBytes` in implementation (do not trust comments).
- **Stripe webhooks:** signature verification exists (check `src/app/api/webhooks/stripe/` in implementation). `StripeEvent` gives idempotency. Payment amounts: verify intents are created server-side from stored invoice balance (see B8).

## B1. Broken access control (OWASP A01)

- **B1.1 Cross-tenant test (automated, new).** New test file `src/lib/__tests__/cross-tenant.test.mts`: for every route + server action that takes an ID (jobs, customers, invoices, quotes, payments, attachments, expenses, projects, crews, equipment, parts, messages, reports), call it as Business B using Business A's IDs. Assert 404 or 403 AND that the response body contains no Business A data (assert on absence of a canary string). Implementation: build the route/action inventory by grepping `src/app/api/**/route.ts` + `src/app/actions/*.ts` for ID params; the test iterates the inventory. This is the highest-value test in Part B — it must be exhaustive, not sampled.
- **B1.2 Role matrix test (automated, new).** After Part A M1 (Memberships), test each role (OWNER, ADMIN, DISPATCHER, TECHNICIAN, CONSUMER, ANONYMOUS) against a matrix of ~30 representative actions. Assert allowed/denied per the A2 role semantics. CONSUMER may only touch their own directory data + linked portal records.
- **B1.3 Mass assignment (automated, new).** For every create/update action, send extra fields: `businessId`, `role`, `ownerId`, `total`, `totalCents`, `status`, `price`, `priceCents`, `voidedAt`. Assert they are rejected (zod strips/ rejects — verify per action) or ignored (stored value unchanged). Fix: every action validates with a zod schema that does NOT include server-controlled fields (use `.strict()` or explicit pick lists; stripped-unknown is not enough — assert the stored row is unchanged).
- **B1.4 Directory claim verification.** Already enforced (claim requires admin approval, `DirectoryClaim.status` + `directoryVerifiedAt`). Test: unapproved listing never appears in public directory results; approved listing appears. Add a test if none exists.
- **B1.5 SSRF (fix).** New `src/lib/ssrf.ts`: `assertPublicUrl(url)` — resolves the hostname via DNS, rejects: private/loopback/link-local/reserved ranges (10/8, 172.16/12, 192.168/16, 127/8, ::1, fe80::/10, 169.254/16 incl. cloud metadata 169.254.169.254), redirects (fetch with `redirect: 'manual'`, reject 3xx to a private host), and non-http(s) schemes. Apply to: outgoing webhook delivery (`src/lib/webhooks.ts`), logo-from-URL (if it exists — grep; if not, mark N/A), link previews (if any — grep). Test: webhook endpoint `http://169.254.169.254/latest/meta-data/` rejected; `http://localhost:3000/hook` rejected (except an explicit test-only allowlist flag); `https://hooks.zapier.com/...` allowed. Note: DNS resolution must happen at fetch time (TOCTOU: DNS rebinding) — implementation uses a custom lookup that validates the resolved IP before connecting, or documents why the hosting fetch cannot do that and pins the validated IP.

## B2. Security misconfiguration (OWASP A02)

- **B2.1 CSP (fix, with a staging gate).** Add a nonce-based CSP in `next.config.ts` (or middleware): `default-src 'self'; script-src 'self' 'nonce-…'; style-src 'self' 'nonce-…'; img-src 'self' blob: data: https:; connect-src 'self' https:; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`. Next.js 16 supports nonces via middleware (`request.headers` → `x-nonce`). Staging gate: deploy to staging, run the full manual QA pass (every page + Copilot + Stripe Checkout + maps + uploads). If any inline script breaks, fix the nonce plumbing — do NOT weaken the policy to `'unsafe-inline'`. If the gate fails after two attempts, fallback = `Content-Security-Policy-Report-Only` + report-uri, documented in SECURITY_REPORT.md.
- **B2.2 `frame-ancestors 'none'` vs SAMEORIGIN (DECISION NEEDED).** Prompt 3 asks for `'none'` (or X-Frame-Options DENY). Current code deliberately uses SAMEORIGIN for future booking-page embedding. X-Frame-Options: keep SAMEORIGIN as a legacy fallback (browsers prefer CSP frame-ancestors).
- **B2.3 Production stack traces (verify).** Confirm `next.config.ts` has no `productionBrowserSourceMaps: true`, error pages render generic messages, and API routes return `{ error: "…" }` without `err.stack`. Test: trigger a 500 on staging, assert the response contains no `at ` stack frames or file paths.
- **B2.4 Debug routes / test pages (remove).** Grep for `/debug`, `/test`, `/playground`, `/__`, dev-only pages. Delete or gate behind an env flag that is OFF in staging/production. List every removed route in SECURITY_REPORT.md.
- **B2.5 Auth provider settings (verify + fix).** Google OAuth: email confirmation on, redirect URLs allowlisted (check `src/lib/google-auth.ts` + Google Cloud console — console settings are a user action, listed as a checklist item for the user, not code). - **B2.6 Preview deployments protected (verify).** Check Vercel project settings: preview deployments require Vercel Authentication (or are public?). If public, enable protection (user action in dashboard — listed as a checklist item). Record the before/after state in SECURITY_REPORT.md. Note: this is a Vercel-dashboard setting, not code.

## B5. Injection (OWASP A05)

- **B5.1 Parameterized queries (verify).** Zero raw SQL today. Rule: no `$queryRaw`/`$executeRaw` without a parameterized query + a comment. Grep in CI (add a CI step that fails if `$queryRaw` appears without a preceding `// parameterized:` comment — or simpler: fails if it appears at all, with an allowlist file).
- **B5.2 `dangerouslySetInnerHTML` (fix).** JSON-LD sites: safe (verify no user content in the JSON — if a business name/description flows into JSON-LD, escape it or assert it is server-controlled). Help article renderer (`src/app/help/[slug]/page.tsx:42`): check `renderBody` — if it does not sanitize, add sanitization (DOMPurify via `isomorphic-dompurify` — NEW DEPENDENCY, needs user approval per project rule; alternative: render help bodies as plain text with a minimal allowlist of `<b><i><a><ul><li>` via a hand-rolled escaper — no dependency. Plan recommends the hand-rolled escaper to avoid a new dependency, with a test proving `<script>`/`<img onerror>` are neutralized).
- **B5.3 XSS test (automated, new).** New test `src/lib/__tests__/xss.test.mts`: inject payloads (`<script>alert(1)</script>`, `<img src=x onerror=alert(1)>`, `"><svg onload=alert(1)>`, `javascript:alert(1)`, `{{7*7}}`) into every text field another person will see: lead description, customer name, job notes, review text, messages, business description. Assert each render surface is safe: web pages (assert the HTML contains the escaped payload, not raw), emails (assert the email body contains escaped payload), PDFs (no PDF generation exists — mark N/A with evidence), CSV exports (see B5.4), Copilot answers (assert the answer renders as text, never raw HTML).
- **B5.4 CSV/Excel formula injection (fix + test).** `src/lib/csv.ts` — verify every cell starting with `=`, `+`, `-`, `@`, `|`, `%` (or containing tab/CR) is neutralized (prefix with `'` or tab, per OWASP CSV Injection). Test: export a customer named `=2+5+cmd|' /C calc'!A0` and assert the CSV cell does not start with `=`. Fix if the neutralizer is missing or incomplete.
- **B5.5 Email header injection (fix + test).** Names/subjects that flow into email headers must strip `\r`/`\n` (and `%0a`/`%0d`). Grep every `Resend` send call; add a `sanitizeHeader()` helper; test with `Subject: hi\r\nBcc: evil@x.com`.

## B7. Authentication failures (OWASP A07)

- **B7.1 Generic errors (verify).** Login: one generic error (done in Part A8 — verify both surfaces). Password reset: always "If an account exists…" (done — verify). Test both with existing + non-existing emails, assert identical responses (status, body, timing within reason).
- **B7.2 Rate limiting with backoff (verify + show test).** DB-backed `RateLimit` exists. Test: N failed logins → 429; assert backoff (increasing delay or lockout window). Cover login, signup, reset, verification. Record the test output in SECURITY_REPORT.md.
- **B7.3 Password policy (fix gaps).** Current: business min 15, customer min 8, no character-type rules (good — matches Prompt 3). Gaps to fix: (a) **breached-password check** — add HIBP k-anonymity check on signup/password-change (SHA-1 prefix, first 5 chars only, over HTTPS — the full password never leaves the server; fallback: if HIBP is unreachable, allow the password and log a warning — fail open on availability, not on security, documented). - **B7.4 TOTP 2FA (fix — biggest B7 item).** New: optional TOTP for every business user (setup: QR code + backup codes, verify flow, disable flow). **Required for owners before they connect payments** — the Stripe Connect flow checks `user.totpEnabled` and blocks with "Enable two-factor authentication first" if off. Test: enroll → verify valid code → reject invalid/expired code → backup code works once → disable requires password. Backup codes: 10 single-use codes, SHA-256 hashed, shown once.
- **B7.5 Sessions (fix gaps).** Current: httpOnly/Secure/SameSite=Lax, ended on logout + password change. Gaps to fix: (a) **rotate on login** (new session id after auth, old session invalidated); (b) **rotate on role change** (Membership role change invalidates that user's sessions); (c) **removing a team member ends their sessions immediately** (Membership status → REMOVED deletes all their Session rows). Test each.
- **B7.6 Email verification before sending to customers (fix).** New: business must verify its email (verification link, 24h expiry) before the platform sends emails to its customers on its behalf. Gate in the send path: unverified business → send refused with "Verify your email first" + a resend-verification action. Test: unverified business send → refused; verified → sent. (Transactional emails TO the business itself — password reset, etc. — are NOT gated.)
- **B7.7 Open redirects (verify).** `safeNext()` exists. Test: `?next=https://evil.com` → redirected to `/` (or the default); `?next=//evil.com` → rejected; `?next=/dashboard` → allowed; `?next=/\evil.com` → rejected. Fix if any case fails.
